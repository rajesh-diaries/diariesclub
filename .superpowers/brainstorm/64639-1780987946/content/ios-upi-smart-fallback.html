iOS UPI: Smart Sequential Fallback

One button. Zero fees. Maximum chance of direct app open.

What happens when the user taps "UPI" on iOS:

Step-by-step flow
1
Try upi://pay?pa=YOUR_UPI_ID&am=500...
✓ Works if any UPI app registered for upi:// (rare on iOS)
✗ Most likely fails silently
2
Try tez://upi/pay?pa=YOUR_UPI_ID... (Google Pay)
✓ Opens Google Pay directly with amount pre-filled
✗ Fails if GPay not installed or scheme changed
3
Try phonepe://pay?pa=YOUR_UPI_ID... (PhonePe)
✓ Opens PhonePe directly with amount pre-filled
✗ Fails if PhonePe not installed or scheme changed
4
Try paytmmp://pay?pa=YOUR_UPI_ID... (Paytm)
✓ Opens Paytm directly with amount pre-filled
✗ Fails if Paytm not installed or scheme changed
5
Fallback: Show QR Code + Copy UPI ID
✓ Works with EVERY UPI app, guaranteed
User scans QR or copies ID → manually pays → comes back → taps "Done"

What the user sees:

Single UPI button (same on Android & iOS)
⚡
UPI — Google Pay, PhonePe, Paytm
Zero fees • Money credited instantly
›

On Android: Tapping this opens the native system chooser with real app icons. One tap, done.

On iOS: The app tries each deep link behind the scenes. If one works, the UPI app opens instantly. If none work, a clean sheet slides up with QR + copy.

Trade-offs to know:

Pros

  • One button everywhere — no platform-specific UI
  • Zero Razorpay fees on UPI
  • Maximum chance of one-tap payment on iOS
  • QR fallback is guaranteed to work
  • No fake app icons — real apps open or QR appears

Cons

  • URL schemes can change without warning
  • Apple may question app-specific deep links during review
  • QR on iOS = more friction than Android
  • Need to declare schemes in Info.plist
